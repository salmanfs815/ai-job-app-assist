# 6. HMAC request signing between the watcher and the API

- Status: Proposed (needs the owner's confirmation before it is shared with the watcher repo)
- Date: 2026-11-09

## Context and problem statement

The job-posting watcher (a separate repository) calls two internal endpoints on this API
(`GET /internal/watch-targets`, `POST /internal/postings:batch`). The shared contract prefers
OAuth 2.0 client credentials with an app role `Postings.Ingest`, and falls back to HMAC request
signing "if External ID tenants do not support client credentials".

## What was verified (2026-11-09, Microsoft Learn)

- External tenants **do** support the client credentials flow, for v2.0 applications.
- But client credentials in an external tenant are billed as the **"M2M Authentication"
  premium add-on**, per token issued. They are not part of the free 50,000 MAU allowance.
  Microsoft's pricing page lists the meter; the per-token price was not shown on the official
  page (third-party sources quote USD 0.001 per token).

An hourly watcher that caches tokens needs about 720 tokens a month. That is small, but it is a
recurring charge and a paid add-on, which the brief rules out ($0 hosting, "do not enable paid
add-ons").

## Considered options

1. Client credentials in the External ID tenant (preferred by the contract, but paid).
2. Client credentials from the **workforce** tenant that already hosts the subscription
   (workload identities there are free), with the API trusting a second issuer.
3. **HMAC-SHA256 request signing** with a shared secret (the contract's fallback).

## Decision (proposed)

Option 3, exactly as specified in the shared contract:

- Headers `X-Watcher-Timestamp` (Unix seconds) and `X-Watcher-Signature` (hex
  HMAC-SHA256) over `timestamp + "\n" + method + "\n" + path + "\n" + sha256_hex(body)`.
- Requests older than 5 minutes (or more than 5 minutes in the future) are rejected; signatures
  are compared in constant time.
- The secret is a Container Apps secret on both sides, generated by Terraform. Two secrets
  may be active at once so it can be rotated without downtime.

Option 2 is a reasonable alternative if the owner prefers tokens: it keeps tokens free but adds
a second trusted issuer to the API. The API's token validator already accepts application
tokens that carry an app role, so switching later is contained.

The `Postings.Ingest` app role still exists on the API registration, and `infra/entra` can create
the watcher's confidential client (`create_watcher_app = true`) if the decision changes.

## Consequences

- Good: $0, no identity-provider dependency for ingestion, simple to test.
- Bad: a shared secret to rotate; no per-client identity beyond "the watcher".
- The contract is unchanged (HMAC is its documented fallback). The internal endpoints and
  their verification are implemented in Phase 2.
